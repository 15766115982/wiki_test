# 02 · KB 契约导读

> 开发者之旅 · 第 2 章。本章**不复述契约**——`spec/spec.zh-CN.md` 是唯一权威，本章只告诉你按什么顺序读、每节为什么存在、和其他部件什么关系。

## 推荐阅读顺序

spec 共 11 节（§0–§10)，按"先建立心智模型，再查细节"的顺序：

### 第一遍：骨架（约 20 分钟）

1. **§0 概述**——五大能力 + 设计原则。读完能向别人解释这个项目。
2. **§2.1 目录树**——KB 的物理结构。`raw/` vs `wiki/` vs `.kb/` 三层职责是整个系统的地基：
   - `raw/` 证据层：1:1 源文档、来源语言、agent 永不改写（只追加/覆盖拉取）;
   - `wiki/` 策展层：govern 所有的结论层，手改不保证存活；
   - `.kb/` 机器衍生品 + 裁决记忆，gitignore——**不进版本控制是刻意的**：它是运行状态，不是知识。
3. **§2.3 wiki 页面 frontmatter 与状态机**——四类页面 + 候选 sidecar 模型。这是全 spec 最重要的一节，与 [04 · 治理与候选状态机](04-治理与候选状态机.md) 对照读。
4. **§4.1 runbook 七步**——治理 run 的完整步骤。和 SKILL.md 第 4 章是同一件事的两种表述：spec 讲"必须发生什么",SKILL.md 讲"agent 具体怎么做"。

## 四类页面：一页全景

| 页型 | 与 raw 的关系 | 身份 | 关键 frontmatter | 构建方式 |
|---|---|---|---|---|
| **source** | 1:1，每篇 raw 必有 | `source_ref` 精确匹配 raw 身份 | `source_ref`、`related_topics`（聚类钩子） | 起草，可子代理并行 |
| **synthesis** | N:1，跨源主题叙事 | slug | `sources`(union 语义） | **增量折叠**，严格串行（见 [03](03-fold机制.md)) |
| **concept** | 跨文档共享抽象的定义 | slug（注册表查重，别名命中即合并） | `sources`、`aliases` | union-merge，同折叠纪律 |
| **entity** | 命名实体 + 类型化关系 | slug | `kind`、`relations`(target 是 slug) | union-merge，同折叠纪律 |

贯穿规则：非 source 页的 `sources` 只并集、`created_at` 永保留；slug 全局唯一、小写 kebab-case、机械校验；正文互链用 Obsidian 兼容的 `[[slug|display]]`，合并时全库机械改写反向链接（`archive/` 除外——冻结记录永不动）。

## 契约的演进纪律

- 契约只**增量兼容**地改；破坏性变更 → CHANGELOG 迁移说明 + 考虑 `contract_version` bump;
- v1.1 改了 `max_sources_per_cluster` 的**语义**（覆盖上限 → 每折批大小）但键名不变、旧 kb.json 照常解析，所以**没有** bump contract_version——这是"语义变了但文件兼容"时怎么处理的活例；
- 每个脚本启动时比对内置契约版本与 kb.json 声明版本，skill 更新于 KB → exit 65 + 迁移指引。

## 术语对齐

改代码前建议过一遍项目根的 `CONTEXT.md`——它是术语表（ubiquitous language)，不收实现决策。当你发现自己在注释里发明"草稿页""临时页"这类词时，停下来查一下：那叫 **candidate / sidecar**。
