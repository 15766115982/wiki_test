# 04 · 治理与候选状态机

> 开发者之旅 · 第 4 章。候选 sidecar 模型是"correctness by structure"原则最集中的体现。契约：spec §2.3、§4.2；执行：SKILL.md ch.4–5。

## 状态机全景

```
                    治理 run 起草
                         │
            ┌────────────┴─────────────┐
            ▼ 低风险(新页/纯追加+无冲突) ▼ 有风险(改写/删除/合并/矛盾/无证据)
        approved                    candidate
        (页面文件)              (*.candidate.md sidecar)
            │                            │
            │                  ┌─────────┼──────────┬─────────┬──────────┐
            │                  ▼ 人裁决  ▼          ▼         ▼          ▼
            │               approve   reject   edit-then-  archive-  keep-both
            │              (原子替换)  (移 archive) approve  loser     (登记平行对)
            ▼                  │          │        │         │
         archived ◀────────────┴──────────┴────────┴─────────┘
        (仅人裁决可达;冻结记录,检索不可见,内部链接永不改写)
```

状态字段的机械约束：页面文件只可能是 `approved | archived`;sidecar 只可能是 `candidate`;`approved → archived` 只能由人裁决触发。**没有任何自动路径能归档一篇已批准页。**

## sidecar 模型解决的原始问题

旧设计（v1.0 前史）：候选直接以覆盖提案形式存在，批准后从 git 恢复旧版（reject-and-restore)。问题：**候选期内 approved 页处于"将被覆盖"的不确定态**，而且恢复逻辑复杂易错。

sidecar 模型的结构性解法：

- 候选 = 目标页旁边的独立文件 `<slug>.candidate.md`，带 `base:`（覆盖锚点 + diff 基底，新页为 `null`，**键必须存在**)和 `review_note:`（为什么是候选，裁决 HTML 首先展示）;
- **approved 页文件永不被候选触碰**——approve 时写临时文件再 rename 原子替换；reject 时把 sidecar 移进 archive，原页根本不需要"恢复"(reject-and-restore 随之退役，见 CONTEXT.md 术语表）;
- **检索不可见性是 glob 排除，不是纪律**：枚举模式 `wiki/{sources,syntheses,concepts,entities}/**` 结构性排除 `archive/`，再机械丢弃 `*.candidate.md`。SKILL.md 检索 Rule 0 明确禁止"枚举全部然后凭意志力跳过"。

## 裁决记忆：`.kb/govern/`

对抗"agent 跨会话无记忆"的结构化补丁，gitignore（运行状态，非知识）:

| 文件 | 内容 | 谁消费 |
|---|---|---|
| `decisions.jsonl` | 全部裁决历史；human 行**强制带 reason**,agent 行强制带 `cited`（先例 id 数组，可为空但键必须在） | `govern-decide.md` 的 few-shot 先例源；裁决 HTML 的"该页历史" |
| `source-tombstones.json` | archive-loser 败方 raw 的墓碑 | acquire:被墓碑压制的 raw 不再拉取（`--force` 可翻案，翻案记 log) |
| `conflict-dismissals.json` | keep-both 登记的平行文档对（规范化、排序存储） | plan：已登记对不再报 conflict-pair |
| `slug-registry.json` / `topic-registry.json` | slug/topic 规范化查存 | 起草时防重复：别名命中 = 确定合并 |
| `runs.jsonl` | run 元数据 | overview 视图的 run 历史 |
| `run.lock` | run 互斥锁，2h 或死进程自动回收 | govern 脚本 |

**先例矛盾 → fail-closed**：同页/同冲突类型出现相反动作的先例时，不平均、不选边——强制进候选交人。judgment 的模糊地带永远向人审方向塌缩。

## 自动化优先的具体机制

治理不是"什么都问人"。`govern-decide.md` prompt 拿先例当 few-shot，先尝试自动裁决重复出现的情况；只有**真正新颖**或**先例矛盾**的案例才进裁决 HTML。衡量这个机制是否在工作的指标：同类案例第二次出现时还打不打扰用户。

## 一个容易踩的坑：review_queue 与 archive

v1.1 修过一个真实 bug:`govern plan` 的 review_queue glob 曾把 `wiki/archive/*.candidate.md`（已归档候选 = 冻结记录）重新捞回待裁决队列。教训：**凡是 glob，先想 archive/ 这个"结构性例外"**——它是 KB 里唯一"内容在 wiki/ 下但语义上不属于 wiki/"的地方。

## 手工改 wiki/ 的检测

plan 的 `human_lists` 里有 hand-edit 检测：diff `wiki/` 与最近一次 `govern: run` 提交。这依赖两个前置纪律：① 每 run 末尾提交 `govern: run <ISO8601>`;② KB 是 git 仓库。所以"KB 必须 git init"不是仪式，是检测机制的传感器。
