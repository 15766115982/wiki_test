# 05 · 实战故事：一次 ADR 编号冲突的完整治理

> 开发者之旅 · 第 5 章。一个真实案例：v1.1 折叠机制第一次大规模实战，以及它拦下的一次真冲突。素材来自一个真实项目（代号 Weft，私有仓库），**已脱敏**——只保留冲突结构，不涉及业务细节。

## 背景

2026-08，某项目用 OpenWiki 在仓库里自动生成了 47 篇 wiki 页（架构总览、各 ADR 决策记录等）。通过 OpenWiki 连接器全部拉入 raw 层 → 一次治理 run 产出：

- **47 篇 source 页**（全部自动批准——新页面，低风险）;
- **9 个簇 → 9 篇 synthesis**:8 篇折叠链全程无冲突，自动批准；
- **1 篇 architecture synthesis 停在候选**——本章主角。

## 冲突长什么样

上游文档集的 ADR 编号在**跨文档引用时不一致**：同一篇决策，文档甲称 ADR-0003，文档乙称 ADR-0004，另有一份索引又指向 ADR-0012。（具体决策内容已略去，结构就是"同一对象，三个编号"。)

这不是 LLM 编造的错误——**上游源文档本身就互相矛盾**。

## 机制如何一环扣一环地接住它

1. **折叠按 `source_version` 升序进行。** 较早的源先折入，页面先采用其中一个编号体系；
2. **折到引用不同编号的源时，矛盾恰好暴露在那一折**——这正是升序折叠的设计意图：冲突定位到具体的源对，而不是混在成品页面里；
3. **semantic-check 输出结构化冲突证据** `{conflicts:[…]}`，点名两个相撞的源；
4. **断链**：最后一个无冲突的折叠保持落盘，问题折变成 sidecar 候选，`review_note` 首行是机器可解析的 `conflict: <kind> | parties: <a> vs <b>`;
5. **裁决报告**把双方并排展示（冲突组），附溯源证据（两源 raw 的原文节录）和该页裁决历史；
6. **剩余源自动顺延**——`簇成员 − 页.sources` 就是下轮的剩余工作，不需要任何人记录"折到第几篇了"。

注意第 4 步的分寸：**系统没有试图"解决"冲突**（它无法知道哪个编号是对的——可能上游自己都没统一），而是把页面停在最后一致状态，把判断题原样交给能判断的人。

## 这个案例验证了哪些设计决策

| 设计 | 验证点 |
|---|---|
| 升序折叠 | 冲突暴露在相撞的那一折，review_note 能精确点名源对 |
| 断链而非中止 | 8 篇 synthesis 不受影响照常落盘；出问题的簇保留最后好状态，不是废墟 |
| 结构化证据强制 | 若 semantic-check 没有输出 `{conflicts}` 结构，按规则会强制候选——本例中它有，所以候选理由精确而非"可疑" |
| 续跑靠结构 | 冲突裁决后，剩余源靠 `页.sources` 游标自然续折，无额外状态 |
| review_note 机器可解析首行 | render 的冲突块直接消费它生成并排对比 |

## 也暴露了边界

这次实战同时是 v1.1 的诞生原因：最初 9 个簇里 7 个在旧截断策略下会产生"未覆盖 N 篇"候选（见 [03 · fold 机制](03-fold机制.md))。**同一批真实数据，先在 v1.0 上证明了截断不可行，再在 v1.1 上证明了折叠可行**——47 篇全量覆盖，只有 1 篇因真冲突进候选。候选率从"7/9 簇"降到"1/9 簇"，且那一个候选是真正有判断价值的。

## 留给读者的思考题

- 如果上游后来修正了编号（统一为 ADR-0003),`source_version` 更新后再次治理，折叠链会如何收敛？（提示：`updated` 的 raw 会让对应 source 页进入 `stale`,synthesis 的哪些折需要重做？)
- 如果你是裁决者，这个案例该选 `edit-then-approve`（统一编号后批准）、`keep-both`（记录上游不一致为已知事实），还是回上游修文档再治理？各自的先例会怎么影响以后的自动裁决？
