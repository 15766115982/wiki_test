# 04 · 日常循环：拉取、治理、裁决

> 使用者之旅 · 第 4 章。上一章是单篇对话的闭环；本章是知识持续生长时的日常节奏。

## 日常节奏一览

```
(不定期) 拉取/蒸馏  →  (攒一批后) 治理  →  (有候选时) 裁决  →  (想看时) 生成站点
   "拉取 …"             "治理"          看 HTML 回 decision      "生成站点"
```

没有定时器、没有后台钩子——所有动作都是你说话触发的。KB 像一个花园：原料随时丢进去，治理是你来修剪的时刻。

## 拉取：多来源汇入

> **拉取 \<选择器\>**

目前实战验证过的连接器是 **OpenWiki 本地连接器**——把代码仓库里自动生成的 wiki 页（`<repo>/openwiki/`）吸进 raw 层：

```
拉取 D:\src\payment-service 的 openwiki
```

脚本路径：`node scripts/acquire.mjs openwiki --repo D:\src\payment-service [--subdir architecture]`

你会看到 `{created, updated, unchanged, removed_upstream, errors}` 的摘要。连接器保证：

- **增量**：只全量拉新增和有变化的；内容 hash 相同的跳过；
- **上游删除有语义**：OpenWiki 里消失的文件直接删 raw（本地文件系统删除是明确的）;Jira/Confluence 则是"两击规则"——连续两次 detect 都找不到才删，防止"没权限"和"被删除"分不清造成误删；
- **每批一个 commit**:`acquire: openwiki (+N ~M -K)`。

（Jira/Confluence 连接器见 [06 · 路线图](06-路线图.md):spec 已完整定义，尚未实战验证。）

## 治理深化：多源折叠出 synthesis

当多篇 source 页共享同一个 topic(frontmatter 里的 `related_topics`)，治理 run 会把它们聚成**簇**，产出或更新一篇 **synthesis 页**——跨源主题叙事，每条结论带 `(raw:来源)` 背书标签。

v1.1 起，synthesis 用**增量折叠**构建，严格串行：

```
折叠第 1 源 → 双闸门校验 → 落盘 → 折叠第 2 源 → 双闸门校验 → 落盘 → …
```

- 每折先读当前页（它是之前所有折叠的累积结果），按 `source_version` 升序折入下一源——**新说法后落，冲突恰好暴露在相撞的那一折**;
- 双闸门：脚本校验（含"重融护栏"——防止重新融合时丢掉原有链接和关键事实）+ 语义检查（必须输出结构化证据 `{conflicts:[…]}` 或 `{no_conflict:true}`，没输出视为没检查）;
- 顺利通过的一折 = 纯追加 → **自动批准**;
- 撞了矛盾 → **断链**：最后一个好的折叠保持不动，相撞的那一折变成候选（review_note 点名相撞的源对），剩余源下轮再折。页的 `sources:` 清单本身就是进度游标，没有额外的状态文件。

**簇没有大小上限**——不会再说"这一簇只覆盖了 6/9 篇"（那条截断规则已在 v1.1 退役，详见 [dev-journey 03](../dev-journey/03-fold机制.md))。

## 裁决：候选回环

治理 run 产生了候选（`*.candidate.md`）时，会生成一份**裁决报告 HTML**（双击打开，单文件、离线可看）。每个案例依次给你看：

1. **review_note**——为什么是候选（高亮在最前）;
2. **diff**——候选 vs 现有页面（红删绿增）;
3. **冲突组**——如果是两源矛盾，双方并排展示；
4. **溯源证据**——可折叠的 raw 原文节录；
5. **该页的裁决历史**——以前怎么判的、理由是什么。

报告**只读，不回写**。你点按钮生成回复文本，粘回会话：

```
decision: approve | page: wiki/concepts/retry-policy.candidate.md | reason: 采纳实现方口径
```

五种动作：`approve`（批准）、`reject`（驳回，候选进 archive)、`edit-then-approve`（改后批准）、`archive-loser`（采纳一方并归档败方，**败方必须显式指定**)、`keep-both`（两方并存，登记为已知平行文档对，以后不再报警）。

你的每个理由都会记入 `.kb/govern/decisions.jsonl`——**理由必填**。这些先例以后会被 agent 引用，让重复出现的同类情况不再打扰你（自动化优先，裁决只在必要时）。

## 健康清单：只报告，不动手

plan 还会产出 `human_lists`：孤儿页、悬空链接、疑似冲突对、**检测到你手工改了 wiki/ 的文件**等。这些**永远不会被自动处置**，只是摆给你看。顺带：`wiki/` 目录是治理所有的，手改不保证存活；想改东西请走"edit-then-approve"裁决通道。

## 动手试试 🔧

教具 KB 里有一篇现成的待裁决候选：

```bash
cat llm-wiki/fixtures/kb/wiki/concepts/retry-policy.candidate.md
```

注意它的 frontmatter:`status: candidate`、`base:`（指向目标页）、`review_note:`（为什么进候选）。再看它的"竞争对手"——已批准页们：

```bash
node llm-wiki/scripts/render.mjs --kb llm-wiki/fixtures/kb report
```

打开生成的 `.kb/govern/reports/latest.html`，就是你在真实裁决时会看到的界面。
