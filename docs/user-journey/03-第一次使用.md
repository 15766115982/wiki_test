# 03 · 第一次使用：从对话到 wiki 页面

> 使用者之旅 · 第 3 章。这是整条旅程的核心闭环：**对话 → 蒸馏 → raw 文档 → 治理 → wiki 页面**。跟完这一章，你就掌握了 80% 的日常用法。

## 场景设定

假设你刚和 Claude 讨论完"订单状态机该怎么设计"，结论包括：五个状态、两条异常路径、为什么不用数据库枚举。这些内容现在只活在这个会话里——会话结束就蒸发。把它变成知识：

## 第 1 步：蒸馏

说一句：

> **蒸馏**（或"**存进 KB**")

agent 会把当前对话（连同它引用过的资料）整理成一篇**蒸馏文档**，落进 `raw/chat/conv-<hash12>.md`。它长这样（结构示意）:

```markdown
---
source: chat
source_id: conv-a1b2c3d4e5f6
source_url: llmwiki://chat/conv-a1b2c3d4e5f6
evidence_class: transcript
---
# 订单状态机设计讨论

- 订单分五态:created → paid → shipped → done,外加 cancelled [T-3]
- 不用数据库枚举,用状态机表,原因:…… [T-7]

# Appendix A(transcript)
### T-3 (user, 2026-08-17T10:02:11Z)
…原文转录…
```

要点：

- **每个要点带引用标记**:`[T-n]` 指向附录 A 的对话转录，`[R-n]` 指向附录 B 的外部引用资料（含出处 URL 和原文节录）。校验是 fail-closed 的——任何一个标记对不上附录，**整篇不写入**，报错重来。
- **诚实声明**：附录是 agent 转录的，不是代码机械生成的；保真度靠 validate 的内部一致性校验 + agent 自律。这点 spec 里明说，文档里也带着这行声明。
- **对话超过 3 万字符会被拒**：不静默截断，提示你按主题分次蒸馏。
- 落 `raw/` 即完成——此时还**检索不到**，要等治理。

## 第 2 步：治理

说一句：

> **治理**

触发一次 govern run。对你这篇新蒸馏文档，run 里发生的事：

1. **plan** 把它列入 `pending`（待消化）清单；
2. **分类**：每篇 raw 至少得到一篇 1:1 的 source 页；内容里提到的"订单状态机"这种跨文档共享概念，会被标记为 concept 种子；
3. **起草原稿**:`wiki/sources/order-state-machine-discussion.md`（示意 slug)，单行 `summary` 喂给索引，`source_ref` 精确指回 raw 身份；
4. **校验 + 语义检查**双闸门：通过后，**新页面属于低风险 → 自动批准落盘**;
5. 若提炼出 concept 页（如 `wiki/concepts/order-state-machine.md`)，先查 slug 注册表防重复，再按同样的纪律处理；
6. **rebuild-index**:`wiki/index.md` 重建，你的新页面出现在索引里；
7. 结尾 agent 会汇报：自动批准了几篇、有几篇等你裁决、健康清单有什么。

治理完，agent 会说"下次治理运行后可检索"的反面——**现在已经可检索了**。

## 第 3 步：问一句试试

直接问（不用任何口令）:

> 订单状态机为什么不用数据库枚举？

agent 会执行检索协议：先读 `wiki/index.md` → 全文搜索关键词变体 → 沿链接和来源链扩展 → 回答，**每个结论带 `[[wikilink]]` 引用**，关键结论带 ≤25 词的原文引用（机器校验过是引用页的原文子串）。末尾附一行检索说明：查了哪些渠道、读了哪几页。

如果 KB 里真没有，它会直说"**KB 中没有此内容**"，而不是编一个。

## 信任分层：蒸馏文档的特殊地位

注意蒸馏文档的 frontmatter 有 `evidence_class: transcript`（转录级证据）。规则：**转录级来源永远不能单独支撑 synthesis 里的一条结论**——必须有拉取级来源（Jira/Confluence/openwiki）佐证，否则整篇 synthesis 强制进候选由你裁决。这是对"对话里说的话可能是错的"这一事实的结构化不信任。

## 动手试试 🔧

用教具 KB 看一篇真实的蒸馏文档和它的引用标记结构：

```bash
cat llm-wiki/fixtures/kb/raw/chat/conv-a1b2c3d4e5f6.md
```

再对照看它被治理后生成的 source 页 `llm-wiki/fixtures/kb/wiki/sources/chat-payment-discussion.md`——注意 frontmatter 里 `source_ref` 如何精确指回 raw 身份，正文如何比 raw 更策展化。

## 常见疑问

**Q：蒸馏完忘了治理，内容会丢吗？**
不会。raw 文档已在 git 仓库里，下次说"治理"时一并消化。

**Q：同一段对话蒸馏两次会怎样？**
`source_id` 是附录内容的哈希前 12 位，同一对话覆盖同一文件，不产生重复。不同对话撞了 id 会报错并加后缀——绝不静默覆盖。

**Q：治理时 KB 里有未提交的 git 改动？**
run 会**暂停**，请你先 commit 或 stash。它绝不替你做破坏性 git 操作。
