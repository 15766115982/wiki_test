# 01 · 这是什么

> 使用者之旅 · 第 1 章。本章纯阅读，约 3 分钟。

## 你大概遇到过这些场景

- 上周和 Claude 讨论清楚了一个技术方案，今天开新会话，它一无所知，你只好把背景重新讲一遍。
- Jira 任务里写"重试 8 次",Confluence 设计文档里写"重试 5 次"——到底哪个对？谁改的？什么时候改的？
- 团队仓库里自动生成的 wiki 页越积越多，但没有一个统一入口能跨仓库、跨来源地问一句"支付回调到底怎么处理的？"

llm-wiki 的答案是：**给 LLM 配一个独立于任何代码仓库的、会自我治理的知识库（KB)，让所有知识先进 KB，再从 KB 里被检索和引用。**

## 四个最重要的设计直觉

读完整条使用者之旅前，先建立这四个直觉，后面每一章都在展开它们：

1. **两层分离：raw 是证据，wiki 是结论。** raw 文档忠实保存来源原文（含原始语言）,wiki 页面是消化后的策展结论。检索只看 wiki 层，但每个结论都能沿 `sources` 链回溯到 raw 证据。

2. **候选制度：agent 不静默改写你的知识。** 新增内容、纯追加且语义检查无冲突的改动可以自动落盘；凡是改写、删除、合并、有矛盾的改动，一律变成 `*.candidate.md` 候选文件，生成一份可视化裁决报告，等你回复"approve / reject / …"。**宁可误伤（把安全的改动也提交给你审），不可放过。**

3. **fail-closed：检查跑不了 = 检查不通过。** 比如没有 Node 环境时，校验脚本跑不了，系统就自动降级为"所有改动都进候选"，而不是跳过校验直接落盘。

4. **记忆在 KB 里，不在会话里。** 你的每一次裁决（为什么批准、为什么驳回）都记在 KB 的 `.kb/govern/decisions.jsonl` 里，成为后续治理判断的先例——这弥补了大模型跨会话无记忆的缺陷。

## 它不适合什么

诚实地说，llm-wiki 不是：

- **通用网页搜索工具**——它只检索你自己的 KB，不替代 Google/官方文档；
- **一次性问答**——问完即走的场景不需要 KB;
- **多人实时协作 wiki**——v1 是单人单 KB 设计，团队场景通过 git 克隆共享，但没有并发合并语义。
