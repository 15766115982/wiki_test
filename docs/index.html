卷首

30 秒看懂这是什么

llm-wiki 是一个 Claude Code / Copilot skill，把散落在各处的知识——对话、Jira、Confluence、仓库 wiki——治理成一个可检索、可裁决、可演化的个人 wiki 知识库（KB)。

它解决的核心问题：LLM 会话是健忘的。今天讨论清楚的设计决策，下周的新会话就忘了；Jira 和 Confluence 里的口径互相矛盾，没人记得以哪个为准。llm-wiki 的做法：

  1. 拉进来——对话蒸馏、连接器拉取，统一成带完整来源元数据的 raw 文档；
  2. 治理成页面——自动消化成四类 wiki 页面，有风险的改动不静默落盘，而是变成「候选」等你裁决；
  3. 读出来——纯 agent 迭代检索（无搜索引擎），每个结论带引用，每个引用机器校验。

整个系统的信任哲学一句话：自动化优先，但拿不准的一定停下来问你（fail-closed)。

项目内各文档的分工

文档读者作用
docs/(本手册)人教学：为什么、怎么上手、怎么读代码
llm-wiki/SKILL.mdLLM(agent)运行时规范：skill 被触发后 agent 照做的唯一权威路径

本手册不复述契约细节——凡涉及字段定义、规则编号处，一律指向 spec 对应小节，spec 是唯一权威来源。

01
使用者之旅 · 第一章

这是什么

纯阅读 · 约 3 分钟

你大概遇到过这些场景

  • 上周和 Claude 讨论清楚了一个技术方案，今天开新会话，它一无所知，你只好把背景重新讲一遍。
  • Jira 任务里写「重试 8 次」,Confluence 设计文档里写「重试 5 次」——到底哪个对？谁改的？什么时候改的？
  • 团队仓库里自动生成的 wiki 页越积越多，但没有一个统一入口能跨仓库、跨来源地问一句「支付回调到底怎么处理的？」

llm-wiki 的答案是：给 LLM 配一个独立于任何代码仓库的、会自我治理的知识库（KB)，让所有知识先进 KB，再从 KB 里被检索和引用。

一张图看全流程

        ┌─────────────────── 外部世界 ───────────────────┐
        │  对话    Jira    Confluence    仓库 openwiki    │
        └───┬────────┬──────────┬────────────┬──────────┘
            │ 蒸馏    │ 拉取      │ 拉取        │ 拉取
            ▼        ▼          ▼            ▼
   ┌─────────────────────────────────────────────────┐
   │ KB(一个独立目录,是 git 仓库)                      │
   │                                                 │
   │   raw/        证据层:1:1 对应源文档,保留原文语言 │
   │     │                                           │
   │     │  治理(govern run,你说「治理」时触发)       │
   │     ▼                                           │
   │   wiki/       策展层:四类页面                    │
   │     ├─ sources/    单源摘要页(与 raw 1:1)       │
   │     ├─ syntheses/  跨源主题叙事(每条结论带来源) │
   │     ├─ concepts/   共享概念的权威定义            │
   │     └─ entities/   命名实体 + 关系               │
   │                                                 │
   │   有风险的改动 → *.candidate.md 候选 → 你裁决    │
   └───────┬───────────────────────────┬─────────────┘
           │ 检索/深研                  │ 生成站点
           ▼                           ▼
   会话内回答(逐条引用)          本地静态 HTML(双击即开)

四个最重要的设计直觉

  1. 两层分离：raw 是证据，wiki 是结论。raw 文档忠实保存来源原文（含原始语言）,wiki 页面是消化后的策展结论。检索只看 wiki 层，但每个结论都能沿 sources 链回溯到 raw 证据。
  2. 候选制度：agent 不静默改写你的知识。新增内容、纯追加且语义检查无冲突的改动可以自动落盘；凡是改写、删除、合并、有矛盾的改动，一律变成 *.candidate.md 候选文件，生成一份可视化裁决报告，等你回复 approve / reject。宁可误伤，不可放过。
  3. fail-closed：检查跑不了 = 检查不通过。比如没有 Node 环境时，校验脚本跑不了，系统就自动降级为「所有改动都进候选」，而不是跳过校验直接落盘。
  4. 记忆在 KB 里，不在会话里。你的每一次裁决（为什么批准、为什么驳回）都记在 KB 的 .kb/govern/decisions.jsonl 里，成为后续治理判断的先例——这弥补了大模型跨会话无记忆的缺陷。

它不适合什么

  • 通用网页搜索工具——它只检索你自己的 KB，不替代 Google/官方文档；
  • 一次性问答——问完即走的场景不需要 KB;
  • 多人实时协作 wiki——v1 是单人单 KB 设计，团队场景通过 git 克隆共享，但没有并发合并语义。

使用者之旅 · 第二章

装起来

目标：装好的 skill + 初始化好的 KB + 配好的环境变量 · 约 10 分钟

前置条件

条件检查方法说明
Claude Code(或 Copilot)—skill 运行的宿主环境
Node.js ≥ 20node --version四个增强脚本需要。没有也能用(SKILL.md 每章都有手动降级路径），但自动校验、自动批准会关闭，体验打折
gitgit --versionKB 必须是 git 仓库（历史追溯、手工改动检测都依赖它）

第一步：安装 skill

skill 的真实位置是 ~/.claude/skills/llm-wiki/(Claude Code 原生读取）。如果你还要给 Copilot 或中性宿主用，运行安装器把它投影过去：

node <skill目录>/scripts/install.mjs            # 首次安装
node <skill目录>/scripts/install.mjs update     # 升级后同步

Windows 优先建 junction,POSIX 优先建 symlink；失败则退化为整目录拷贝（带版本戳）。输出里 mode: junction | symlink | copy 告诉你用了哪种方式。装完后新开一个会话，说一句「初始化 KB」，看 skill 是否被触发——能触发即安装成功。

第二步：初始化 KB

在会话里说一句「初始化 KB」,agent 会引导你走完五步（每步都会先问你再动手）。这里把你会被问到的事先说清楚：

  1. KB 放哪？默认建议 ~/kb。这是个独立全局目录，故意不放进任何代码仓库——换项目工作时知识不丢。
  2. 创建目录树:raw/（证据层）、wiki/（策展层）、.kb/（机器衍生品，gitignore)、kb.json、GOVERNANCE.md、log.md。
  3. git init——必须是 git 仓库。
  4. 设置环境变量(Windows 示例，新终端生效）:
    setx LLM_WIKI_KB "C:\Users\<你>\kb"
    之后每个会话自动发现 KB，零废话。多 KB 是 v1 的明确边界——--kb 参数是内置的逃生口。
  5. 写 kb.json。最小可用配置（不用 Jira/Confluence 时）:
{
  "contract_version": 1,
  "language": "zh",
  "connectors": {},
  "governance": { "max_clusters_per_run": 10, "max_sources_per_cluster": 1, "max_chars_per_source": 2500 }
}

language: zh 表示 wiki 页面用中文写；raw 层永远保留来源原文语言。三个 governance 值是默认值可省略；注意 max_sources_per_cluster 是每折折入几篇源（默认 1，推荐保持），不是覆盖上限。

如果你拿到了别人 git clone 给你的 KB：跳过建目录，只需确认 kb.json 存在、设置 LLM_WIKI_KB 即可。

第三步：验证

说一句「蒸馏」，然后随便聊几句，再说「把刚才的存进 KB」。如果 raw/chat/ 下出现了一篇 conv-xxxxxxxxxxxx.md，链路就通了——这是唯一不需要任何外部账号的验证路径。

不想动真 KB？仓库里带了一个教具 KB，先跑个体检：

cd D:\claude\kb-skill
node llm-wiki/scripts/govern.mjs --kb llm-wiki/fixtures/kb plan

这个 fixtures KB 是一个虚构的「支付」领域示例：4 篇 raw（支付库表设计、回调重试讨论……)、已批准的 wiki 页面、一篇待裁决的候选 wiki/concepts/retry-policy.candidate.md。plan 输出的六个列表（待消化/异常/错误/待裁决队列/健康清单/被抑制）就是第 4 章要讲的治理入口视图。

03
使用者之旅 · 第三章

第一次使用：从对话到 wiki 页面

整条旅程的核心闭环：对话 → 蒸馏 → raw 文档 → 治理 → wiki 页面

场景设定

假设你刚和 Claude 讨论完「订单状态机该怎么设计」，结论包括：五个状态、两条异常路径、为什么不用数据库枚举。这些内容现在只活在这个会话里——会话结束就蒸发。把它变成知识：

第 1 步：蒸馏

说一句「蒸馏」（或「存进 KB」)。agent 会把当前对话（连同它引用过的资料）整理成一篇蒸馏文档，落进 raw/chat/conv-<hash12>.md。它长这样（结构示意）:

---
source: chat
source_id: conv-a1b2c3d4e5f6
source_url: llmwiki://chat/conv-a1b2c3d4e5f6
evidence_class: transcript
---
# 订单状态机设计讨论

- 订单分五态:created → paid → shipped → done,外加 cancelled [T-3]
- 不用数据库枚举,用状态机表,原因:…… [T-7]

# Appendix A(transcript)
### T-3 (user, 2026-08-17T10:02:11Z)
…原文转录…
  • 每个要点带引用标记:[T-n] 指向附录 A 的对话转录，[R-n] 指向附录 B 的外部引用资料（含出处 URL 和原文节录）。校验是 fail-closed 的——任何一个标记对不上附录，整篇不写入，报错重来。
  • 诚实声明：附录是 agent 转录的，不是代码机械生成的；保真度靠 validate 的内部一致性校验 + agent 自律。这点 spec 里明说，文档里也带着这行声明。
  • 对话超过 3 万字符会被拒：不静默截断，提示你按主题分次蒸馏。
  • 落 raw/ 即完成——此时还检索不到，要等治理。

第 2 步：治理

说一句「治理」，触发一次 govern run。对你这篇新蒸馏文档，run 里发生的事：

  1. plan 把它列入 pending（待消化）清单；
  2. 分类：每篇 raw 至少得到一篇 1:1 的 source 页；内容里提到的「订单状态机」这种跨文档共享概念，会被标记为 concept 种子；
  3. 起草原稿:wiki/sources/order-state-machine-discussion.md（示意 slug)，单行 summary 喂给索引，source_ref 精确指回 raw 身份；
  4. 校验 + 语义检查双闸门：通过后，新页面属于低风险 → 自动批准落盘;
  5. 若提炼出 concept 页（如 wiki/concepts/order-state-machine.md)，先查 slug 注册表防重复，再按同样的纪律处理；
  6. rebuild-index:wiki/index.md 重建，你的新页面出现在索引里；
  7. 结尾 agent 会汇报：自动批准了几篇、有几篇等你裁决、健康清单有什么。

第 3 步：问一句试试

直接问（不用任何口令）:「订单状态机为什么不用数据库枚举？」agent 会执行检索协议：先读 wiki/index.md → 全文搜索关键词变体 → 沿链接和来源链扩展 → 回答，每个结论带 [[wikilink]] 引用，关键结论带 ≤25 词的原文引用（机器校验过是引用页的原文子串）。末尾附一行检索说明：查了哪些渠道、读了哪几页。如果 KB 里真没有，它会直说「KB 中没有此内容」，而不是编一个。

信任分层：蒸馏文档的特殊地位

注意蒸馏文档的 frontmatter 有 evidence_class: transcript（转录级证据）。规则：转录级来源永远不能单独支撑 synthesis 里的一条结论——必须有拉取级来源（Jira/Confluence/openwiki）佐证，否则整篇 synthesis 强制进候选由你裁决。这是对「对话里说的话可能是错的」这一事实的结构化不信任。

用教具 KB 看一篇真实的蒸馏文档和它的引用标记结构：

cat llm-wiki/fixtures/kb/raw/chat/conv-a1b2c3d4e5f6.md

再对照看它被治理后生成的 source 页 llm-wiki/fixtures/kb/wiki/sources/chat-payment-discussion.md——注意 frontmatter 里 source_ref 如何精确指回 raw 身份，正文如何比 raw 更策展化。

常见疑问

Q：蒸馏完忘了治理，内容会丢吗？
不会。raw 文档已在 git 仓库里，下次说「治理」时一并消化。

Q：同一段对话蒸馏两次会怎样？
source_id 是附录内容的哈希前 12 位，同一对话覆盖同一文件，不产生重复。不同对话撞了 id 会报错并加后缀——绝不静默覆盖。

Q：治理时 KB 里有未提交的 git 改动？
run 会暂停，请你先 commit 或 stash。它绝不替你做破坏性 git 操作。

使用者之旅 · 第四章

日常循环：拉取、治理、裁决

知识持续生长时的日常节奏

日常节奏一览

(不定期) 拉取/蒸馏  →  (攒一批后) 治理  →  (有候选时) 裁决  →  (想看时) 生成站点
   「拉取 …」             「治理」          看 HTML 回 decision      「生成站点」

没有定时器、没有后台钩子——所有动作都是你说话触发的。KB 像一个花园：原料随时丢进去，治理是你来修剪的时刻。

拉取：多来源汇入

目前实战验证过的连接器是 OpenWiki 本地连接器——把代码仓库里自动生成的 wiki 页（<repo>/openwiki/）吸进 raw 层：

口令:「拉取 D:\src\payment-service 的 openwiki」; 脚本路径：

node scripts/acquire.mjs openwiki --repo D:\src\payment-service [--subdir architecture]

你会看到 {created, updated, unchanged, removed_upstream, errors} 的摘要。连接器保证：

  • 增量：只全量拉新增和有变化的；内容 hash 相同的跳过；
  • 上游删除有语义:OpenWiki 里消失的文件直接删 raw（本地文件系统删除是明确的）;Jira/Confluence 则是「两击规则」——连续两次 detect 都找不到才删，防止「没权限」和「被删除」分不清造成误删；
  • 每批一个 commit:acquire: openwiki (+N ~M -K)。

(Jira/Confluence 连接器见 第 6 章 · 路线图:spec 已完整定义，尚未实战验证。)

治理深化：多源折叠出 synthesis

当多篇 source 页共享同一个 topic(frontmatter 里的 related_topics)，治理 run 会把它们聚成簇，产出或更新一篇 synthesis 页——跨源主题叙事，每条结论带 (raw:来源) 背书标签。v1.1 起，synthesis 用增量折叠构建，严格串行：

折叠第 1 源 → 双闸门校验 → 落盘 → 折叠第 2 源 → 双闸门校验 → 落盘 → …
  • 每折先读当前页（它是之前所有折叠的累积结果），按 source_version 升序折入下一源——新说法后落，冲突恰好暴露在相撞的那一折;
  • 双闸门：脚本校验（含「重融护栏」——防止重新融合时丢掉原有链接和关键事实）+ 语义检查（必须输出结构化证据 {conflicts:[…]} 或 {no_conflict:true}，没输出视为没检查）;
  • 顺利通过的一折 = 纯追加 → 自动批准;
  • 撞了矛盾 → 断链：最后一个好的折叠保持不动，相撞的那一折变成候选（review_note 点名相撞的源对），剩余源下轮再折。页的 sources: 清单本身就是进度游标，没有额外的状态文件。

簇没有大小上限——不会再说「这一簇只覆盖了 6/9 篇」（那条截断规则已在 v1.1 退役，详见 dev-journey 03 · fold 机制)。

裁决：候选回环

治理 run 产生了候选（*.candidate.md）时，会生成一份裁决报告 HTML（双击打开，单文件、离线可看）。每个案例依次给你看：

  1. review_note——为什么是候选（高亮在最前）;
  2. diff——候选 vs 现有页面（红删绿增）;
  3. 冲突组——如果是两源矛盾，双方并排展示；
  4. 溯源证据——可折叠的 raw 原文节录；
  5. 该页的裁决历史——以前怎么判的、理由是什么。

报告只读，不回写。你点按钮生成回复文本，粘回会话：

decision: approve | page: wiki/concepts/retry-policy.candidate.md | reason: 采纳实现方口径

五种动作：approve（批准）、reject（驳回，候选进 archive)、edit-then-approve（改后批准）、archive-loser（采纳一方并归档败方，败方必须显式指定)、keep-both（两方并存，登记为已知平行文档对，以后不再报警）。

你的每个理由都会记入 .kb/govern/decisions.jsonl——理由必填。这些先例以后会被 agent 引用，让重复出现的同类情况不再打扰你（自动化优先，裁决只在必要时）。

健康清单：只报告，不动手

plan 还会产出 human_lists：孤儿页、悬空链接、疑似冲突对、检测到你手工改了 wiki/ 的文件等。这些永远不会被自动处置，只是摆给你看。顺带：wiki/ 目录是治理所有的，手改不保证存活；想改东西请走「edit-then-approve」裁决通道。

教具 KB 里有一篇现成的待裁决候选：

cat llm-wiki/fixtures/kb/wiki/concepts/retry-policy.candidate.md

注意它的 frontmatter:status: candidate、base:（指向目标页）、review_note:（为什么进候选）。再生成裁决报告看看真实界面：

node llm-wiki/scripts/render.mjs --kb llm-wiki/fixtures/kb report

打开生成的 .kb/govern/reports/latest.html，就是你在真实裁决时会看到的样子。

视图看什么

检索：问就完了

普通问题直接问，不用口令。检索协议的六个要点（对使用者而言你只需感知到这些行为）:

  1. 索引先行——先读 wiki/index.md 建全局地图；
  2. 多路召回——全文搜索 + 文件名匹配，查询词自动做同义词和中英交叉扩展；禁止编造「假想文档」当查询（禁 HyDE)，只允许从已命中页提取新关键词再查（CSQE);
  3. 图扩展——命中页沿 wikilink 和来源链各扩一跳（synthesis 命中会拉进它的 sources 交叉验证）;
  4. 迭代加深——按标题分节读，最多 3 轮，不整篇吞；
  5. 引用纪律——只从读过的页作答，每条结论带 [[wikilink]]；关键结论带 ≤25 词原文引用，机器校验是原文子串才输出；零命中直说「KB 中没有此内容」;
  6. 检索说明——答案末尾一行账目：查了哪些渠道、读了哪几页。

例:「支付回调重试几次？」

Jira 任务说 8 次（[[pay-callback-retry]]);Confluence 设计文档说 5 次（[[pay-table-design-v3]]);synthesis [[payment]] 记录了裁决后的结论……

检索说明： queried [full-text: "重试","retry"; index]; read [[payment]] (+2 via:provenance)

注意这个例子里系统没有掩盖矛盾——两个来源不一致时，把两边都摆出来并指向裁决记录，正是 KB 的价值。

深研：强制拉满迭代

口令「深研 <问题>」。普通提问是「单档自适应」(agent 按问题复杂度自己选轮数）；加上「深研」二字 = 强制最大多轮迭代，适合「把 KB 里关于 X 的一切都挖出来」这类问题。

看不见的东西同样重要

检索只看 approved 页面，而且是结构性保证：候选文件（*.candidate.md）和 archive/ 在枚举时就被 glob 机械排除，不靠 agent 自觉。含义：

  • 候选里的内容（可能正确但未经你确认）不会混进答案；
  • 被驳回/归档的旧说法不会复活；
  • 如果你发现答案漏了什么，先想想：那篇内容是不是还躺在候选队列里等你 approve?

规模上限：协议按 ≤500 页设计。超出后有分节读索引、二级 topic 索引等降级策略（CHANGELOG 的 known boundaries 有说明）。

node llm-wiki/scripts/render.mjs --kb llm-wiki/fixtures/kb site

  • 在 graph 视图找到 synthesis 页 payment，看它和四篇 source 页之间的连线（这些语义边来自 frontmatter 的 sources:，不是正文链接）;
  • 在 history 视图看裁决时间线——fixtures 里的 decisions.jsonl 记录了一次真实的 approve/reject 序列。

架构总览

给要改这个 skill 的人:先建立地图,再谈细节

最重要的架构事实：这不是一个程序，是一份给 agent 的 runbook

llm-wiki/
├── SKILL.md        ← 唯一规范路径:skill 被触发后,agent 照它执行一切(507 行)
├── prompts/        ← 9 个 prompt 模板,在 SKILL.md 各步骤按文件名引用
├── scripts/        ← 5 个 Node 零依赖单文件脚本,渐进增强,不是必需品
├── templates/      ← 页面骨架(4 类 wiki 页 + raw)+ 2 个 HTML 模板
└── fixtures/       ← 教具 KB + 上游仓库样本,测试和本手册共用

设计原则（SKILL.md §1，贯穿一切）:

  1. prompts first——判断性工作全部由宿主 agent(LLM）执行；脚本是省力的机械部分；
  2. scripts as progressive enhancement——没有 Node 环境，SKILL.md 每章有写到「agent 可照做粒度」的手动降级路径；
  3. fail-closed——检查跑不了 = 检查不通过 → 进候选交人审；
  4. correctness by structure, not by discipline——正确性靠目录结构/glob 排除/frontmatter 白名单机械保证，不靠「agent 记得不要做某事」。

第 4 条是这个项目的灵魂，读代码时用它当试金石：凡是看到「检索排除候选」靠的是 glob 模式而不是提示词叮嘱，看到「approved 页永不被候选覆盖」靠的是 sidecar 文件模型而不是警告——都是这条原则的落实。

fold 机制：v1.1 为什么用折叠取代截断

理解当前代码形态的钥匙 · 故事见 CHANGELOG [1.1.0],契约见 spec §4.1 steps 3–4

问题：截断策略在第一次真实使用中崩了

v1.0 的设计：synthesis 一次性覆盖整个簇，但设了 ≤6 源的上限，装不下就截断，并在下一轮把「未覆盖 N 篇」列为强制候选。

第一次真实使用（Weft 项目，47 篇 openwiki raw）的证据：9 个簇里 7 个撞了上限，裁决队列被 "N sources not covered" 候选淹没。每个候选都要人看，但人能做的决定无非是「好，下轮继续」——这不是判断，是确认噪音。设计原则「自动化优先，只在必要时裁决」被自己的实现违反了。

解法：把「一次覆盖」改成「增量折叠」

核心想法来自版本控制：与其一次性写一篇大页面，不如每次折入一个源，每折过闸门，页面是折叠链的累积结果。

fold 1:  ∅ ──折入源 A──▶ 页面 v1 ──双闸门──▶ 落盘
fold 2:  页面 v1 ──折入源 B──▶ 页面 v2 ──双闸门──▶ 落盘
fold 3:  页面 v2 ──折入源 C──▶ 冲突!──▶ 断链:v2 保持,C 折进候选

每折的纪律（spec §4.1 step 4)

  1. 先读当前页——它是之前所有折叠的 merge base。跳过这次读取就是契约违规(agent 提示词层面强制）;
  2. 按 source_version 升序读下一源——旧说法先进，新说法后落。为什么升序？让冲突恰好暴露在相撞的那一折：如果新文档改口了，你会在折入它的那一折看到它和既有页面矛盾，而不是事后发现页面里有两种说法；
  3. union-merge:sources 只并集，created_at 保留，正文重新融合时优先把新源的结论作为带来源标签的追加，而不是整体重写（护栏机械检查这一点）;
  4. 双闸门，每折必过:
    • validate.mjs --file，含重融护栏(refusion-retention guardrail)：新页面若丢掉 base 的 wikilink/sources，或 >20% 关键事实行消失 → 校验失败；
    • semantic-check.md，必须输出结构化证据 {conflicts:[…]} 或 {no_conflict:true}——没有结构化输出 = 没有检查 = 强制候选。

断链与续跑

  • 断链：矛盾 / 护栏破损 / 无结构化证据 → 链停在这一折：最后好页保持，问题折落候选（review_note 首行 conflict: <kind> | parties: <a> vs <b>，机器可解析，render 的冲突块靠它），剩余源下轮续；
  • 续跑靠结构，无游标文件：页面 frontmatter 的 sources: 就是游标。簇成员 − 页.sources = 下轮的剩余工作。少一个状态文件，就少一个会和现实漂移的状态。

风险红线的相应修订

通过全部闸门的一折（①sources 只并 ②护栏过 ③明确 no_conflict）视同纯追加 → 可自动批准。注意 no_conflict 从来不是单独放行理由：改写/删除即使语义检查无冲突也强制候选。

设计层面的三个收获（可迁移到别的项目)

  1. 把人审从「流程的常态产物」中摘出去。截断策略让每个大簇必然产生人审；折叠策略让人审只在真有矛盾时出现。衡量自动化设计健康度的指标：每 run 产生的候选里，「需要判断」和「只需确认」的比例。
  2. 批量上限换成增量批次，语义完全不同。max_sources_per_cluster 从「这一簇最多覆盖几篇」（覆盖上限 → 必然截断）变成「每折折入几篇」（批大小 → 覆盖总是全量）。键名没改、kb.json 不 bump——兼容性靠「旧值在新语义下仍然合法」达成。
  3. 进度编码进数据结构，而不是进度文件。sources: 清单天然就是游标。当你想引入一个 progress.json 时，先问：现有结构里有没有一个字段已经在记录同样的事？

代码里的落点

  • 折叠纪律的提示词载体：prompts/draft-synthesis.md(v1.1 fold-mode 重写）、prompts/draft-concept.md、prompts/extract-entity.md;
  • 机械闸门：scripts/validate.mjs（重融护栏在 govern 检查集里）;
  • 串行纪律：SKILL.md ch.4 step 3.10 明确子代理并行只适用于 source 页起草——非 source 页永不并行；
  • 折叠顺序的语义：source_version 升序，见 spec §4.1。

治理与候选状态机

「correctness by structure」原则最集中的体现 · 契约:spec §2.3、§4.2

状态机全景

                    治理 run 起草
                         │
            ┌────────────┴─────────────┐
            ▼ 低风险(新页/纯追加+无冲突) ▼ 有风险(改写/删除/合并/矛盾/无证据)
        approved                    candidate
        (页面文件)              (*.candidate.md sidecar)
            │                            │
            │                  ┌─────────┼──────────┬─────────┬──────────┐
            │                  ▼ 人裁决  ▼          ▼         ▼          ▼
            │               approve   reject   edit-then-  archive-  keep-both
            │              (原子替换)  (移 archive) approve  loser     (登记平行对)
            ▼                  │          │        │         │
         archived ◀────────────┴──────────┴────────┴─────────┘
        (仅人裁决可达;冻结记录,检索不可见,内部链接永不改写)

状态字段的机械约束：页面文件只可能是 approved | archived;sidecar 只可能是 candidate;approved → archived 只能由人裁决触发。没有任何自动路径能归档一篇已批准页。

sidecar 模型解决的原始问题

旧设计（v1.0 前史）：候选直接以覆盖提案形式存在，批准后从 git 恢复旧版（reject-and-restore)。问题：候选期内 approved 页处于「将被覆盖」的不确定态，而且恢复逻辑复杂易错。

sidecar 模型的结构性解法：

  • 候选 = 目标页旁边的独立文件 <slug>.candidate.md，带 base:（覆盖锚点 + diff 基底，新页为 null，键必须存在）和 review_note:（为什么是候选，裁决 HTML 首先展示）;
  • approved 页文件永不被候选触碰——approve 时写临时文件再 rename 原子替换；reject 时把 sidecar 移进 archive，原页根本不需要「恢复」(reject-and-restore 随之退役）;
  • 检索不可见性是 glob 排除，不是纪律：枚举模式 wiki/{sources,syntheses,concepts,entities}/** 结构性排除 archive/，再机械丢弃 *.candidate.md。SKILL.md 检索 Rule 0 明确禁止「枚举全部然后凭意志力跳过」。

裁决记忆：.kb/govern/

对抗「agent 跨会话无记忆」的结构化补丁，gitignore（运行状态，非知识）:

文件内容谁消费
decisions.jsonl全部裁决历史；human 行强制带 reason,agent 行强制带 cited（先例 id 数组，可为空但键必须在）govern-decide.md 的 few-shot 先例源；裁决 HTML 的「该页历史」
source-tombstones.jsonarchive-loser 败方 raw 的墓碑acquire：被墓碑压制的 raw 不再拉取（--force 可翻案，翻案记 log)
conflict-dismissals.jsonkeep-both 登记的平行文档对（规范化、排序存储）plan：已登记对不再报 conflict-pair
slug-registry.json / topic-registry.jsonslug/topic 规范化查存起草时防重复：别名命中 = 确定合并
runs.jsonlrun 元数据overview 视图的 run 历史
run.lockrun 互斥锁，2h 或死进程自动回收govern 脚本

先例矛盾 → fail-closed：同页/同冲突类型出现相反动作的先例时，不平均、不选边——强制进候选交人。judgment 的模糊地带永远向人审方向塌缩。

自动化优先的具体机制

治理不是「什么都问人」。govern-decide.md prompt 拿先例当 few-shot，先尝试自动裁决重复出现的情况；只有真正新颖或先例矛盾的案例才进裁决 HTML。衡量这个机制是否在工作的指标：同类案例第二次出现时还打不打扰用户。

一个容易踩的坑：review_queue 与 archive

v1.1 修过一个真实 bug:govern plan 的 review_queue glob 曾把 wiki/archive/*.candidate.md（已归档候选 = 冻结记录）重新捞回待裁决队列。教训：凡是 glob，先想 archive/ 这个「结构性例外」——它是 KB 里唯一「内容在 wiki/ 下但语义上不属于 wiki/」的地方。

手工改 wiki/ 的检测

plan 的 human_lists 里有 hand-edit 检测：diff wiki/ 与最近一次 govern: run 提交。这依赖两个前置纪律：① 每 run 末尾提交 govern: run <ISO8601>;② KB 是 git 仓库。所以「KB 必须 git init」不是仪式，是检测机制的传感器。

开发者之旅 · 第五章

实战故事：一次 ADR 编号冲突的完整治理

真实案例,已脱敏——只保留冲突结构,不涉及业务细节

背景

2026-08，某项目（代号 Weft，私有仓库）用 OpenWiki 在仓库里自动生成了 47 篇 wiki 页（架构总览、各 ADR 决策记录等）。通过 OpenWiki 连接器全部拉入 raw 层 → 一次治理 run 产出：

  • 47 篇 source 页（全部自动批准——新页面，低风险）;
  • 9 个簇 → 9 篇 synthesis:8 篇折叠链全程无冲突，自动批准；
  • 1 篇 architecture synthesis 停在候选——本章主角。

冲突长什么样

上游文档集的 ADR 编号在跨文档引用时不一致：同一篇决策，文档甲称 ADR-0003，文档乙称 ADR-0004，另有一份索引又指向 ADR-0012。（具体决策内容已略去，结构就是「同一对象，三个编号」。)

这不是 LLM 编造的错误——上游源文档本身就互相矛盾。

机制如何一环扣一环地接住它

  1. 折叠按 source_version 升序进行。较早的源先折入，页面先采用其中一个编号体系；
  2. 折到引用不同编号的源时，矛盾恰好暴露在那一折——这正是升序折叠的设计意图：冲突定位到具体的源对，而不是混在成品页面里；
  3. semantic-check 输出结构化冲突证据 {conflicts:[…]}，点名两个相撞的源；
  4. 断链：最后一个无冲突的折叠保持落盘，问题折变成 sidecar 候选，review_note 首行是机器可解析的 conflict: <kind> | parties: <a> vs <b>;
  5. 裁决报告把双方并排展示（冲突组），附溯源证据（两源 raw 的原文节录）和该页裁决历史；
  6. 剩余源自动顺延——簇成员 − 页.sources 就是下轮的剩余工作，不需要任何人记录「折到第几篇了」。

注意第 4 步的分寸：系统没有试图「解决」冲突（它无法知道哪个编号是对的——可能上游自己都没统一），而是把页面停在最后一致状态，把判断题原样交给能判断的人。

这个案例验证了哪些设计决策

设计验证点
升序折叠冲突暴露在相撞的那一折，review_note 能精确点名源对
断链而非中止8 篇 synthesis 不受影响照常落盘；出问题的簇保留最后好状态，不是废墟
结构化证据强制若 semantic-check 没有输出 {conflicts} 结构，按规则会强制候选——本例中它有，所以候选理由精确而非「可疑」
续跑靠结构冲突裁决后，剩余源靠 页.sources 游标自然续折，无额外状态
review_note 机器可解析首行render 的冲突块直接消费它生成并排对比

也暴露了边界

这次实战同时是 v1.1 的诞生原因：最初 9 个簇里 7 个在旧截断策略下会产生「未覆盖 N 篇」候选（见 03 · fold 机制)。同一批真实数据，先在 v1.0 上证明了截断不可行，再在 v1.1 上证明了折叠可行——47 篇全量覆盖，只有 1 篇因真冲突进候选。候选率从「7/9 簇」降到「1/9 簇」，且那一个候选是真正有判断价值的。

留给读者的思考题

  • 如果上游后来修正了编号（统一为 ADR-0003),source_version 更新后再次治理，折叠链会如何收敛？（提示：updated 的 raw 会让对应 source 页进入 stale,synthesis 的哪些折需要重做？)
  • 如果你是裁决者，这个案例该选 edit-then-approve（统一编号后批准）、keep-both（记录上游不一致为已知事实），还是回上游修文档再治理？各自的先例会怎么影响以后的自动裁决？

已知问题（诚实的待办)

  • install.test.mjs 拷贝模式漂移测试 1/8 失败——v1.1 前就存在、未调查。不是 v1.1 引入的回归，但它躺在那里等着有人查。想为项目做贡献？这是个很好的第一题。

扩展指南

加一个新 connector（如 Zephyr Scale、GitLab wiki)

  1. spec §3 加一节连接器规范：选择器形式、认证、增量语义、删除语义（两击还是直接删？)、附件策略；
  2. scripts/acquire.mjs 加实现——遵守共同约定：stdout JSON、退出码、detect-first、commit 纪律、错误消息精确无密钥；
  3. raw frontmatter 的 source 白名单加新值（spec §2.2 + validate.mjs);
  4. fixtures 加样本，acquire.test.mjs 加用例；
  5. SKILL.md ch.3 加 CLI 形式和手动降级路径（用户粘贴内容时 agent 怎么手工归一化——这是最容易被忘的一步）。

加/改一个 prompt 模板

  1. prompts/ 下新建或修改，保持「结构化输出契约」传统（如 semantic-check 的 {conflicts}/{no_conflict})——无结构化输出 = 未执行是 fail-closed 的支柱；
  2. SKILL.md 对应步骤点名引用文件名；
  3. spec §4.3 模板清单同步；
  4. 没有直接单测——e2e 是兜底。改 prompt 后至少手动跑一遍完整治理验证。

改契约（字段/规则）

最高纪律区：spec 双语两版同步 → 评估 contract_version(v1.1 的「语义变、键名不变、不 bump」是参照案例）→ SKILL.md → validate.mjs → 模板 → CHANGELOG（破坏性变更必须带迁移说明）→ 本手册（见下）。

文档同步约定

本手册不是契约权威——spec 和 SKILL.md 才是。项目根的 CONTEXT.md 里有一条约定：改 spec / SKILL.md / CHANGELOG 时必须检查 docs/ 是否受影响。如果你在 Claude 会话里改这些东西，agent 会主动提醒你；如果你手工改，请自觉执行。

收尾：开发者之旅的三句话总结

  1. SKILL.md 是规范，脚本是增强，prompts 是判断——改东西先想清楚动的是哪一层；
  2. 一切正确性尽量下沉为结构(glob 排除、sidecar、白名单、原子 rename)，提示词叮嘱是最后手段；
  3. 人审是最贵资源——每个设计决策都值得问：这会产生「只需确认」的候选噪音吗？
